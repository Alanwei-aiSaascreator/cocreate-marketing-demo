# 系统说明书 · 商家 × AI × 老客 共创营销 Demo

> 这份文档回答三个问题：**这套系统整体是怎么转的**、**每个设计决策背后的思路是什么**、
> **用到/踩到了哪些技术知识点**。
>
> 所有数字和结论都来自仓库里可复跑的验证脚本（`node scripts/smoke-test.mjs` 52 项、
> `pnpm verify:promises` 12 项），不是描述性文字。

---

## 0. 先对齐：这个系统在回答什么问题

面试题要求设计一套「商家用 AI 做跨平台营销内容、与老客共创、并回馈贡献用户」的系统，
本地可跑、可部署。

本仓库是它的**可运行答案**，刻意只做**玩法闭环**，把四类重模块明确后置（见 §7）。

**核心主张一句话**：

> 纯 AI 写稿会撞上「同质化」和「太假」两堵墙；解法不是把提示词写得更花，
> 而是**把老客拉进来提供 AI 造不出来的东西（真实体验 + 实拍图），AI 只负责加工和适配**。
> 但共创有两个必须踩住的坑：**放开自由发挥会崩质量与合规**，**交稿就给钱会退化成廉价刷稿**。

这两个坑的解法，就是本系统真正的技术含量所在。

## 1. 整体逻辑

### 1.1 闭环全景

```

 │                                            ├─ 生成各平台内容框架             │
 │                                            ├─ 生成轻量任务卡（只让填空）      │
 │                                            └─ 建议奖励阶梯（阈值由规则定）    │
 │                                                                             │
 ├─ 分享 H5 链接 / 门店二维码 ────────────────────────────────────────────────► │

 │                                            ┌───────────────────────────────┤
 │                                            ├─ 风控校验（查重/灌水/截流/禁词） │

 │◄─ 内容库（逐条可追溯素材来源）─────────────┤                                │

 ├─ 采用内容                                                                     │

 └──────────────── 陌生访客点开分享 → 贡献值自动 +5（封顶 50）◄──────────────────┘
```

### 1.2 数据在每一步落到哪张表

| 步骤 | 写入的表 | 关键字段 |
|---|---|---|
| 商家建店 | `Merchant` | `tones` / `sellingPoints` / `bannedWords`（都是 JSON 字符串） |
| AI 生成三件套 | `Campaign` | `frames`（平台框架）、`taskCard`（任务卡）、`rewardTiers`（奖励阶梯） |
| 老客进入 H5 | `Contributor` | `viewerToken`（免登录身份），免账号体系 |
| 提交素材 | `Submission` | `answers`、`imageUrl`、`imageHash`、`riskFlags`、`points` |
| AI 加工 | `GeneratedContent` | `platform` × `variant`（llm/rule 两版共存）、`shareToken`、`publishedAt` |
| 记贡献 | `Contribution` | `breakdown`（逐项可解释）、`firstClaimKey`（一次性资源名额） |
| 发福利 | `Reward` | `code`、`status`（issued/redeemed/expired） |
| 归因 | `TrackEvent` | `type`（view/share/click/submit）、`viewerKey`（访客指纹） |
| 运行时设置 | `Setting` | 浏览器里填的 AI 密钥（键值对，优先级高于 `.env`） |

共 **9 张表**。设计取舍见 §3.7。

### 1.3 四个关键角色的边界

- **商家**定的是**边界**：调性、卖点、合规禁词、平台、奖励预算。
- **AI** 定的是**结构与表达**：内容框架、任务卡字段、各平台语气与篇幅。
- **规则引擎**定的是**经济规则**：分数怎么算、阈值是多少。**这部分刻意不交给模型**（原因见 §3.2）。
- **老客**提供的是**事实**：他真实吃到、看到、拍到的。这是整条链路上 AI 造不出来的部分。

## 2. 核心思路：两个坑怎么踩住

### 坑一：完全放开让用户自由发挥 → 内容质量和合规会崩

**做法：不给白纸，只给填空题。**

AI 生成的不是「一段要写什么的说明」，而是一张**结构化任务卡 `TaskField[]`**：

```jsonc
{
  "id": "feeling",          // 固定语义名，系统按它计分
  "label": "这次吃下来最想说的是什么",
  "type": "textarea",       // textarea | text | choice | image
  "required": true,
  "maxLength": 80,          // 逼出「短而真」
  "why": "为什么这样设计（给商家看的说明）"
}
```

三条硬约束落在提示词里（`lib/ai/prompts.ts`）：

1. **4–5 个字段，老客 30 秒内能填完**；
2. **文字类字段一律设 `maxLength`**；
3. **必须包含一个 `image` 字段**（实拍图是可信度的地基）。

**合规边界**是商家录入的 `bannedWords`，在两个地方生效：

- 老客自己写的禁词 → 风控标记为 `warn`，并**如实告诉他** AI 会替换；
- AI 加工时 → 规则引擎**真的替换**（长且无歧义的词替换、短词保留并标出，避免改出病句）。

> 这一条被 `verify:promises` 钉住了。原本注释写着「已自动替换禁词」，代码里却只标记不替换 ——
> 属于**撒谎注释**，已修正并加回归测试。

### 坑二：简单「交稿就给钱」→ 廉价刷稿，对卖货没帮助

**做法：分数可拆解、分级绑定真实贡献、并且真的会回落。**

| 项目 | 分值 | 设计意图 |
|---|---|---|
| 提交合格素材 | +20 | 保底，鼓励开口 |
| 提供实拍图 | +10 | 权重刻意给高：可信度地基 |
| 补充具体细节 | +5 | 细节是 AI 编不出来的东西 |
| 素材完整度高 | +5 | 引导填满而非敷衍 |
| 首次参与本活动 | +10 | 新人加权，第一次就能拿到第一档 |
| **内容被商家采用** | **+30** | **质量导向：只有真被用起来才给** |
| **带来有效点击回流** | **+5/次，封顶 50** | **奖励绑定真实引流效果** |
| 图片重复 | −20 | 惩罚，但只扣分不封号 |
| 超出便捷次数（第 4 次起） | 基础分 20 → **5** | 鼓励「少而真」而不是凑分 |

三条最容易做假的机制，这里都是**真的**：

1. **超出次数真的降分** —— 不是只在提示文案里说说。`verify:promises` 实测：第 1 次基础分 20，第 4 次真降到 5。
2. **采用才给 +30** —— 提交即全额会退化成刷稿。
3. **点击真的会改变奖励** —— 见 §3.5，点击 → 事务加分 → 重新结算 → 当场可能解锁一张券。

**成本控制**：奖励只用**店铺福利**（`Reward.type` 只有 `coupon` / `gift`，代码层面不出现现金），
单项封顶 50，并且**奖励阈值由规则强制映射**（见 §3.2）。

## 3. 知识点逐层拆解

### 3.1 AI 层：一个可降级的适配器

**为什么必须可降级**：AI 能力是**外部依赖**，会超时、限流、欠费、返回不合法 JSON。
如果业务逻辑直接依赖它，这些故障会变成用户侧的功能故障。所以 AI 层被设计成一个**接口稳定、实现可替换**的适配器。

```
LLM_MODE=auto（默认）  有 key 走模型；失败 → 自动降级到内置规则引擎
LLM_MODE=llm（严格）   必须走模型，失败直接抛错 —— 用于验证模型链路，不允许静默降级
LLM_MODE=rule（强制）  全程规则引擎 —— 演示时可现场切换对比
```

**知识点：什么才算「降级」。** 这是本项目最容易写错的地方。

`degraded = true` **只在「配了 key 但模型调用失败/返回不合法」时为真**。
种子数据、没配 key 走规则引擎，都**不算**降级 —— 那是**按设计**。

> 为什么较真：如果不区分这两者，后台的「AI 生成质量」面板会永远显示一大片红色降级，
> 数字就变成了噪音，运营看不出真正的故障。

**知识点：静默降级为什么危险。** 用户拿到的是「看起来正常」的模板产出，但没人知道模型挂了。
本系统的处理是**让失败必然可见**：

- 每条 `GeneratedContent` 逐条记录真实来源 `aiMode` + `degraded` + `aiNote`；
- **逐条**而不是整批写一个值 —— 模型可能只返回了部分平台，其余是规则引擎补的，
  整批写同一个值会让模板内容在库里被标成「大模型产出」；
- 后台面板区分「按设计走规则」与「真降级」，并给出明确健康结论（健康 / 部分降级 / 全不降级）。

**知识点：两版并存用于对比。** 同一份素材、同一个平台**可以同时存两版**
（`variant: llm | rule`），各有独立 `shareToken`。

`isPrimary` 字段存在的唯一理由：**质量面板只能统计 primary**。
如果两版都计入，比例会变成假的 50/50 —— 那比不统计更误导人。
对比版不进内容库计数、不进漏斗、不参与质量比例。

### 3.2 提示词工程：边界比文采重要

**知识点：事实边界必须写死。** 最容易发生的失效模式是
**模型把「商家卖点」写成「老客的第一人称体验」** —— 老客根本没吃过那道菜，内容却有鼻子有眼。

提示词里因此有明确铁律：

> 只使用素材里出现的事实。老客没提到的菜、价格、服务、环境，一个字都不许编。
> 第一人称体验（我吃了 / 我看到）只能来自素材，一字不许加。

修正后的效果是可验证的：模型会写「他们家还有凌晨到的鲜毛肚，**下次来试试**」——措辞停在「下次」，
而不是伪装成已经吃过的体验。

**知识点：经济规则不能交给模型。** 实测踩过的坑：让模型生成奖励阈值，它给出 `1/3/5` 这种量级，
而单次提交就能拿 50 分 → **老客提交一次就解锁全部福利，商家预算瞬间被击穿**。

原因很简单：**模型不知道本系统的积分尺度**。所以改成：

- AI 只负责写**档位名、福利内容、面额**；
- 阈值一律由 `canonicalThresholds()` 强制映射到预设阶梯（`[50]` / `[50,150]` / `[50,120,260]` / `[50,100,180,300]`）。

一句话原则：**AI 出内容，规则定经济。**

### 3.3 计分与激励：可拆解是第一原则

**知识点：分值必须能对用户解释。** 一个黑盒数字不会让任何人改变行为。
所以每次结算都产出 `PointItem[]`（`{label, points, note}`），并在 H5 上**逐项写给老客看**：

```
+20  提交合格素材     保底分，鼓励参与 —— 先愿意开口，才谈得上共创
+10  提供实拍图       实拍图是可信度的地基，也是各平台判定真实内容最认的信号
+5   补充了具体细节   细节是 AI 编不出来的东西，也是这套内容区别于纯 AI 写稿的地方
+10  首次参与本活动   新人加权，让老客第一次参与就能拿到第一档福利
```

**知识点：奖励进度也要可见。** H5 上直接显示「再拿多少分能解锁福利」，
把「怎么做才能拿更多」讲清楚，比事后发钱有效。

**知识点：撤销采用必须收回券。** 商家撤销「采用」会让贡献值回落 −30，
但老客可能已经靠这 30 分越过档位、拿到券了。如果只收分数不收回券，
账本上就会出现**一张没有贡献支撑的券**。所以有 `expireDowngradedRewards()`：

- 只作废 `issued` 状态的券；
- **已核销的不能追溯作废**（老客已经到店用掉了）；
- 找不到对应档位（阶梯被重新生成过）时不擅自作废，交给商家判断。

### 3.4 并发正确性 —— 本项目技术含量最高的部分

**知识点：应用层的「先查后插」在并发下必然失效。**

```ts
const exists = await prisma.contribution.findFirst({ where: { submissionId, reason } });
if (!exists) await prisma.contribution.create({ ... });   // ← 两个请求都会查到「没有」
```

而代码注释当时还写着「反复点采用不会重复加分」—— **承诺是假的**。

**解法：把幂等下沉为数据库约束，应用层查询只作快速路径。**

```prisma
Reward            @@unique([campaignId, contributorId, tierName])   // 同档位只发一次
Contribution      @@unique([submissionId, reason])                  // 同素材同理由只记一次
GeneratedContent  @@unique([submissionId, platform, variant])       // 同素材同平台同引擎只一条
TrackEvent        @@unique([contentId, type, viewerKey])            // 同访客同内容只计一次
Contribution      firstClaimKey String? @unique                     // 「首次参与」的名额
```

**知识点：P2002 的处理原则。** 只吞**预期内的唯一冲突**，其它错误必须照抛 ——
静默吞掉数据库故障会让「券没发出去」变得无声无息。

**知识点（最微妙的一条）：「首次参与 +10」为什么比其他三条难。**

前三条的冲突对象是「同一份素材 / 同一条内容」，一个唯一键就够。
而它的冲突对象是**一对（活动, 老客）** —— 两次并发提交的 `submissionId` **本来就不同**，
`@@unique([submissionId, reason])` 根本挡不住：两个请求都会数到「本活动还没提交过」，各加 10 分。

解法是让数据库**发名额**：

```ts
const firstClaimKey = priorCount === 0 ? `first:${campaignId}:${contributorId}` : null;
try {
  await prisma.contribution.create({ data: { ..., firstClaimKey } });   // 抢到了
} catch (err) {
  if (!firstClaimKey || !isUniqueViolation(err)) throw err;             // 其它错误照抛
  finalScore = scoreSubmission({ ...scoreInput, priorSubmissions: 1 }); // 去掉这 10 分重算
  await prisma.submission.update({ ... points: finalScore.points });    // 同步改正已落库的分值
  await prisma.contribution.create({ data: { ..., firstClaimKey: null } });
}
```

两个细节值得注意：

1. **重算要用同一份 `scoreInput`** —— 重新手拼参数很容易漏项（比如忘掉 `hasImage`，
   就会把实拍图那 10 分算没）。
2. **响应必须返回 `finalScore` 而不是 `score`** —— 否则界面显示给老客的分数会比他实际拿到的多，
   那又是一次「承诺与行为不一致」。

**知识点：封顶必须放进事务。** 点击加分用 `$transaction` 包住「读已得分 → 判断封顶 → 写入」，
并发下不会超发。

### 3.5 引流归因：让「奖励绑定真实效果」不只是口号

**知识点：`TrackEvent` 是归因钩子。** 这张表让整条链路可追踪：

```
老客分享（复制文案） → 陌生访客打开分享页（view）→ 点 CTA（click）→ 贡献值 +5 → 可能当场解锁一张券
```

**知识点：访客身份必须稳定 —— 这里踩过一个大坑。**

最初用 middleware 注入的 `x-cc-viewer` 当身份。但那个 token 在 cookie 缺失时
是**每次请求现场新生成的 UUID** —— 脚本只要不带 cookie，每次都能拿到全新身份，
「同访客只计一次」形同虚设，连发 10 次就能刷满封顶。

修正：**只认稳定来源** —— 真实 cookie，没有就退化用 `IP + User-Agent` 的哈希。

**知识点：自点不计。** 贡献者自己点自己的分享不计分（真的去查了 contributor）。
这条也在冒烟测试里被断言钉住。

**知识点：浏览量记「独立访客数」而不是累加。** 靠唯一约束天然去重，
这比累加更有意义，同时挡住刷量。

### 3.6 风控与合规：每条判定都要能解释

8 条规则，全部产出**可读的理由**（`RiskFlag { code, label, level, note }`），而不是一个 true/false：

| code | level | 触发条件 |
|---|---|---|
| `duplicate_image` | warn | 同活动内图片 sha256 重复 |
| `duplicate_text` | warn | 文本答案与历史提交完全一致 |
| `low_quality_text` | warn | 过短 / 连续重复字符 / 纯符号无实质中文 |
| `contact_leak` | **block** | 命中联系方式或外链正则（私域截流） |
| `banned_words` | warn | 命中商家配置的合规禁词 |
| `rate_limit` | warn | 本活动累计提交达到便捷次数 |

**知识点：惩罚要可解释才有约束力。** 被 block 的素材不进内容库、不计分，
但**告诉用户为什么、以及怎么改**。

**知识点：图片处理的三个坑。**

1. **格式以文件头（魔数）为准，不信客户端声明的 Content-Type** —— 否则把任意二进制标成
   `image/png` 就能穿过白名单。顺带给出 HEIC 的明确提示（手机拍照最常见的失败原因）。
2. **前端压缩**：手机直出照片常有 3–12MB，超过后端上限。H5 里用 canvas 缩到长边 1600px +
   JPEG 0.82，顺带把 iPhone 的 HEIC 统一转成 JPEG。
3. **先校验后落盘**：落盘必须等到「确认要入库」那一刻。原来先落盘再校验必填，
   老客漏填一个字段就会在 `public/uploads/` 留下**没有任何记录引用的孤儿图**，且没有回收路径。
   现在若写盘后发生异常，会 `unlink` 掉刚写的文件。

### 3.7 数据建模：SQLite 的三个限制与应对

**知识点：SQLite 不支持 enum / Json / 数组。** 所有结构化字段统一用 `String` 存 JSON，
在 `lib/json.ts` 里做类型化读写。这样**换成 Postgres 时字段无需改动**，
只需改 `provider` 和把这些列迁到 `Json` 类型。

**知识点：冗余缓存列是纯负债。** `Contributor.totalPoints` 被删掉了 ——
它只写不读（榜单和 H5 都用 `aggregate` 重算），每次结算多一次无用 UPDATE，
而且一旦哪条路径漏了更新就会与真实数据**静默不一致**。

**知识点：什么时候该加唯一约束，什么时候不该。**
约束是用来保护**业务上不可重复的资源**（一次性的名额、同一档位的一张券），
而不是用来「顺便」表达业务规则。所以 `Contribution` 上同时存在两个约束，
各管一件事，互不越界。

### 3.8 工程与可验证性：把「承诺」变成回归测试

**知识点：撒谎注释比 bug 更坏。** 它让读代码的人（包括未来的自己）建立错误的心智模型。

本项目实测发现过 4 处「注释/文案声称做了某事，代码里却没做」：

1. `LLM_MODE=llm` 声称「失败即报错」，实际会静默降级；
2. 风控提示声称「超出部分不计入有效贡献」，代码里没有任何实现；
3. 禁词提示声称「AI 会替换」，规则引擎只标记不替换；
4. `compare-engines.ts` 声称模型不可用时会报错暴露，实际正常退出。

全部改对后，用 `pnpm verify:promises`（12 项）**钉住，避免退化回去**。

**知识点：测试要能诊断，不只是能失败。**
冒烟测试原先把非 JSON 响应直接 `res.json()`，报错只有一句 `Unexpected token '<'` ——
完全看不出是哪个请求、什么状态码、服务端说了什么。现在会报出状态码 + 响应片段，
并在识别到 HTML 时**直接把已知根因和处置方式写进报错**。

**知识点：断言要确定性，不要靠碰运气。**
并发保护用「重复插入期望 P2002」这种**确定性**断言，而不是「碰运气触发竞态」。
另外，光有约束不够 —— 还要断言「**提交接口确实在占用这个名额**」，
否则约束只是一条没人走的空规则。

### 3.9 取舍：为什么不做「一键发布」

四个平台都**没有**面向第三方的图文发布接口。做一个「一键同步全平台」的按钮非常容易，
但那是一句兑现不了的承诺 —— 追问一句「你调的是哪个开放平台接口」就穿了。

所以改成**半自动**，把真实流程压到最短，每一步都真的有用：

1. 一键复制文案/标签、下载实拍图；
2. 打开平台创作页（**没有网页入口的平台如实说明只能走 App**，不给点进去没用的链接）；
3. 回来标记「已发布」→ 落库到 `publishedAt`。

第 3 步不是装饰：**没有它，商家永远不知道内容到底发出去了没有**。
两版产出可以分别发布，于是能拿来做真实的 A/B 对比。

## 4. 一次完整请求的全链路

### 4.1 老客提交素材（最重的一步，一次请求串完五件事）

`POST /api/c/[token]/submit`：

```
1. 校验活动状态（失效 / 已结束给不同的人话提示）
2. 按任务卡清洗答案（防超长、防脏数据）
3. 读图片进内存 + 魔数校验真实格式  ← 此刻还不落盘
4. 必填校验（图片必填时单独给一句人话）
5. 认人（免登录 viewerToken）
6. 风控：同活动内图片 hash 查重 + 文本查重 + 灌水 + 截流 + 禁词 + 频次
7. 计分（可拆解）
8. 到这一步才真正把图片落盘     ← 前面任何 return 都不会留下孤儿文件
9. 落库（被 block 则标记 rejected 并直接返回）
10. AI 多平台加工（失败自动降级，不影响老客拿福利）
11. 逐条写入 GeneratedContent（逐条记真实来源）
12. 记贡献（抢「首次参与」名额，冲突则重算）
13. 结算：重算累计 → 补齐奖励档位（数据库唯一约束兜底防重复发券）
```

### 4.2 点击回流

`POST /api/track`：

```
1. 用稳定身份（cookie 或 IP+UA 哈希）落一条 click 事件，靠唯一约束去重
2. 自己点自己的分享 → 记录但不计分
3. 事务内：读该素材已得引流分 → 判断封顶 → 写入贡献
4. 重新结算 + 作废因分数回落而不够格的券
```

### 4.3 采用 / 撤销采用

`POST /api/merchant/submissions/[id]/adopt`：更新内容 `adopted` → 幂等加 30 分 →
重新结算 → **撤销时作废不再够格的券**。

### 4.4 扫码核销

老客在「我的福利」出示券码二维码 → 商家扫码 → `/merchant/redeem/[code]` →
落到这一张券 → 点一下核销（`status=redeemed`，留下 `redeemedAt`）。

> 原来只能在后台奖励列表里翻到那张券再点，老客得在柜台前干等。
> 扫码直达才是一笔真实交易该有的节奏。

## 6. 明确的边界与已知限制

### 明确不做（后置的重模块）

- **真实多平台一键发布** —— 无开放接口，改成半自动并如实标注；
- **精细效果归因** —— 需要平台侧数据回传，现用分享链接的 view/click 上报；
- **自动结算打款** —— 涉及资金合规，且主张奖励只用店铺福利；
- **完整风控反刷** —— 现有图片 sha256 查重 + 频次限制 + 灌水检测 + 私域截流；
- **账号体系** —— 老客侧改用免登录 token，刻意降低参与门槛；商家侧只有最简口令保护。

### 已知限制（如实记录）

- 内容生成的**事实边界仍靠提示词约束，不是硬校验**。生产环境应再加一层
  「素材实体比对」：命中了素材里不存在的人财物就转人工复核。
- **感知哈希**未做：现用文件内容 sha256，能挡住同一张图重复提交，
  挡不住裁剪或加水印后的二次上传。
- 抖音的标题与「前 3 秒钩子」内容有重复，属可接受但可优化项。
- 规则引擎产出是模板拼装，调性差异不如真模型明显 —— 它是**安全网**，不是替代品。
- 商家的最简口令保护**不是生产方案**：缺资源归属校验（核销时确认这张券属于当前商家）
  与写接口限流。

---

## 7. 如果继续做，优先级建议

1. **事实边界硬校验**（素材实体比对）—— 这是当前最大的质量风险，且提示词兜不住；
2. **套餐/团购核销与订单打通** —— 让「到店核销」直接对应一笔真实收入归因；
3. **感知哈希 + 图像相似度检索** —— 补上二次上传的漏洞；
4. **商家资源归属校验 + 写接口限流** —— 把最简口令升级为可用方案。
