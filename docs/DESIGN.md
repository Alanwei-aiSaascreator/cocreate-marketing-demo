# 设计决策与踩坑记录

这份文档记录的是**为什么这么做**，以及**实际做的时候踩到了什么**。
产品说明和运行方式看 [README](../README.md)。

## ADR-1 · AI 层做成「可降级的适配器」而不是直接调模型

**背景**：Demo 要在面试现场演示。现场可能断网、key 可能欠费或限流、模型可能返回不合法的 JSON。

**决策**：`lib/ai/index.ts` 对外只暴露 `generateBlueprint()` 和 `composeContents()` 两个函数，
内部走 `LLM_MODE=auto`：有 key 走模型，**任何一步失败都降级到 `lib/ai/rules.ts` 的规则引擎**，
返回结构完全一致，`aiMode` 字段如实标注走了哪条。

**代价与理由**：
- 代价是要维护两套产出逻辑（约 400 行规则引擎）。
- 收益有两条：演示不会再开天窗；而且**规则引擎本身就是一条质量下限** ——
  模型不可用时产出仍然是「模板 + 老客真实素材拼装」，不是一句「AI 生成失败」。
- 关键细节：降级**不静默**。界面和接口都明说这次是"规则引擎生成"，不糊弄。

**另一层防御**：模型返回的 JSON 会经过
① 去围栏 / 截取花括号 / 修多余逗号的容错解析 → ② zod 结构校验 → ③ 显式归一化。
漏平台、漏图片字段、阈值离谱，都会在 ③ 被补齐，而不是让下游流程崩掉。

## ADR-2 · 模型输出是「不可信输入」，不给它标严格类型

**背景**：最初用 `z.infer<typeof schema>` 直接把模型输出的类型当成领域类型。
结果 zod 的 `.catch()` 让推断类型退化成 `unknown`，`tsc` 报了一串错。

**当时的诱惑**：加几个 `as` 就过去了。

**实际决策**：这个类型错误其实指向了一个真实的设计问题 ——
**模型输出本来就是不可信输入，给它标严格类型本身就是撒谎**。

改为：zod 只负责"形状对不对、核心字段在不在"，校验通过后得到的是**宽松类型**
（`RawPlatformFrame` / `RawTaskField` / `RawRewardTier`），
再由 `ensureFrames()` / `ensureTaskCard()` / `ensureRewardTiers()` 显式转成严格领域类型。
`llmJson<T>()` 的 schema 参数改成不带泛型的 `ZodType`，由调用方显式声明 `T`。

这样"归一化"从一个隐含动作变成了一个**显式的、可读的步骤**。

## ADR-3 · 奖励阈值属于经济规则，不让模型决定

**背景（实测踩坑）**：真实调用模型生成活动蓝图，产出的奖励阶梯是：

```json
[{"threshold": 1, "name": "参与礼"}, {"threshold": 3, "name": "优质内容礼"}, {"threshold": 5, "name": "共创达人礼"}]
```

**问题**：本系统的贡献值尺度是 —— 提交一份合格素材单次就能拿 50 分（基础 20 + 实拍图 10 + 细节 5 + 完整 5 + 首次 10）。
阈值 1 / 3 / 5 意味着**老客提交一次就解锁全部三档福利，商家预算瞬间被击穿**。

**根因**：模型不知道我们的积分尺度，它按"1-5 分"的直觉给阈值。

**决策**：调提示词（把积分经济写清楚并锚定 50~300）**只是第一层**，
真正的兜底是在 `lib/domain/scoring.ts` 里定义 `canonicalThresholds(n)`：

```
1 档 → [50]      3 档 → [50, 120, 260]
2 档 → [50, 150] 4 档 → [50, 100, 180, 300]
```

`ensureRewardTiers()` 保留模型写的**档位名、福利内容、面额**（这是它擅长的），
但 `threshold` 一律强制映射到这个阶梯上（这是确定性的）。

**原则**：**AI 出内容，规则定经济。** 凡是"算得出来"的东西，不要交给模型。
提示词里也同步写明了积分经济和"不要自己发明量级"，让模型的档位语义（尝鲜 → 常客 → 铁粉）合理。

## ADR-4 · 严格区分「第一人称体验」和「店铺客观信息」

**背景（实测踩坑）**：老客提交的素材里只有**锅底**和**冰粉**（服务员送冰粉的细节），
但模型产出的小红书正文里出现了：

> **2. 凌晨到的鲜毛肚：毛肚是当天凌晨到的鲜货，下锅几秒就能吃，脆得很直接。**

老客根本没提交过毛肚 —— 模型把我在 `mustInclude` 里写的**商家卖点**，当成了老客的体验写进了「真实体验」分点里。

**严重性**：这条直接打脸整个产品主张（"不编造老客没提到的体验"），
而且是**我自己的设计自相矛盾**：一边在框架里要求"必含卖点"，一边在加工提示词里要求"只用素材事实"。

**决策**（两处一起改）：
1. `prompts.ts` 的 `COMPOSE_SYSTEM` 里加死规则：第一人称体验只能来自素材；
   店铺客观信息可以来自商家资料，但**必须写成客观陈述**（「他们家主打 X」），
   绝不能写成「我吃了 X，很香」；老客没提到的招牌只能作为店铺介绍一笔带过，
   不得出现在「真实体验」「推荐」这类第一人称分点里。
2. `rules.ts` 的 `mustInclude` 里，商家卖点明确标注为
   「**只能作客观店铺信息提及，不得写成老客的亲身体验**」。

**修复后实测效果**：

| 平台 | 修复前 | 修复后 |
| --- | --- | --- |
| 小红书 | 「毛肚…下锅几秒就能吃，脆得很直接」（第一人称分点） | 正文只讲锅底和冰粉，正文完全不提毛肚 |
| 抖音 | 「毛肚是凌晨到的鲜货，下锅几秒就脆」（口播） | 「他们家还有凌晨到的鲜毛肚，**下次来试试**」 |
| 点评 | 混在「推荐」里 | 「另外店里主打凌晨到的鲜毛肚，**新鲜度是卖点**」 |

模型开始主动承认自己没吃过 —— 这个区别就是"共创"和"AI 编稿"的分界线。

**遗留限制**：这仍然是**提示词约束，不是硬校验**。生产环境应再加一层
「素材实体比对」：把产出里的菜名/价格/服务描述与素材做实体级比对，命中素材中不存在的就转人工复核。

## ADR-5 · 贡献值必须「可拆解」，而不是一个黑盒数字

**决策**：`scoreSubmission()` 产出的不是一个数字，而是 `PointItem[]`：每条得分都有
`label`（做了什么）、`points`（多少分）、`note`（**为什么给这个分**）。

```
提交合格素材          +20   保底分，鼓励参与
提供实拍图            +10   实拍图是可信度的地基
补充了具体细节        +5    细节是 AI 编不出来的东西
素材完整度高          +5    必填项全部填写
首次参与本活动        +10   新人加权，让第一次参与就能拿到第一档福利
图片重复              -20   同活动内已收到过相同图片
──────────────────────────
内容被商家采用        +30   质量导向（采用时追加）
带来有效点击回流      +5/次 绑定真实引流效果（封顶 50）
```

**为什么**：这套机制要同时约束两方，而两方都需要"讲得通"：
- 老客要看到「怎么做才能拿更多」，否则不会持续贡献；
- 商家要看到「这笔钱花在哪了」，否则不敢放预算。

所以界面上（H5 结果页、贡献明细、素材与风控 Tab）每一处都展示完整拆解和原因。

## ADR-6 · 引流归因用一张 `TrackEvent` 表兜住

**决策**：每条 AI 内容带一个 `shareToken`，分享落地页 `/s/[shareToken]` 在加载时记 `view`、
点 CTA 时记 `click`，`click` 触发贡献值 +5。

**为什么这是必需品而不是加分项**：没有它，"奖励绑定真实引流效果"就只是 PPT 上的一句话。
有了它，演示时能当场发生：面试官用手机点一下，贡献者的贡献值在商家后台的贡献榜上当场变化。

**三条防刷规则**（都在 `app/api/track/route.ts`）：
1. 同一个访客对同一条内容只计一次有效回流（按 viewerToken 去重）
2. **自己点自己的分享不计分** —— 否则这条链路的分数毫无意义
3. 单项封顶 50 分 —— 避免一条爆款内容把商家的福利预算打穿

## ADR-7 · 免登录身份：cookie 要在**本次请求**就能被读到

**背景**：老客要免登录参与，就不能有账号体系。用 `middleware.ts` 下发一个 `cc_viewer` cookie 来认人。

**踩到的细节**：写 `response.cookies.set()` 只对**下一次**请求生效，
首次访问的服务端组件读不到这个 cookie，于是"第一次进来的人不知道自己是谁"，
提交时才会创建身份，导致页面上的"我的贡献值"永远是 0。

**解决**：middleware 在写 response cookie 的同时，把 token 塞进请求头 `x-cc-viewer` 转发下去；
`lib/viewer.ts` 的 `readViewerToken()` **优先读请求头、退化读 cookie**。
这样首次访问和后续访问的行为一致。

## ADR-8 · 不引外部字体、不引第三方二维码服务

**决策**：放弃 `next/font/google`（create-next-app 默认带 Geist），改用系统字体栈；
二维码用 `qrcode` 包在服务端出图，不请求外部生成服务。

**理由**：都是为了**构建期和运行期不依赖外网**。字体下载失败会让整个 Demo 掉样式，
这在演示场景里是不可接受的失败模式。"能离线跑"是这个项目的硬约束。

## ADR-9 · 逐条校验，别让一个字段吃掉整批 AI 产出

**背景（实测踩坑）**：老客提交素材后，界面一切正常、贡献值和福利照常发放，
但内容库里的东西全是模板拼的 —— 大模型明明配置正常。

翻 `aiNote` 才看到真正的原因：

```
模型调用失败，已自动降级到规则引擎。
原因：结构校验失败: contents.3.title String must contain at least 1 character(s)
```

模型返回了 4 条内容，但**第 4 条（朋友圈）的 `title` 是空的** ——
朋友圈本来就没有标题，模型留空完全合理。而我那条 `title: z.string().min(1)`
让**整批 4 个平台一齐被判失败**，全部退回模板。

**这是 AI 层最危险的失败模式**：不是报错、不是崩溃，而是**静默降级** ——
界面上看不出任何异常，但产品的核心主张（AI 加工质量）已经完全落空。
如果不是我习惯性去打 `aiNote`，它会一直藏着。

**决策**（三处一起改）：

1. **容器只管形状，元素逐条校验。**
   `blueprintSchema` / `composeBundleSchema` 从
   `z.array(itemSchema).min(n)` 改成 `z.array(z.unknown())`，
   元素由 `parseEach()` 逐条 `safeParse`：坏一条只丢那一条，由规则引擎单独补齐。

2. **区分「字段缺失」和「字段为空」。**
   标题这类**平台语义上允许为空**的字段改为 `.catch("")`，
   再由归一化补兜底值（正文首行 → 平台名）。
   真正不能空的（`body`）才保持 `min(1)`。

3. **如实汇报，不假装是 AI 产出的。**
   模型一条可用的都没给出时，`aiMode` 标成 `rule` 而不是 `llm`；
   `aiNote` 里明确写出「丢弃 N 项不合法产出」「N 个平台由规则引擎补齐」。

**配套的回归断言**（`scripts/smoke-test.mjs`）：读 `.env` 判断是否配置了 key，
若配置了，就断言 `aiMode === "llm"` 且 `aiNote` 里不出现「降级/补齐/不合法」。
**静默降级从此不可能再悄悄回来。**

**顺带发现**：同一条测试里，重复使用同一张图片提交时贡献值从 50 掉到 30 ——
不是 bug，是 `duplicate_image` 扣 20 分的防刷规则正确生效。

## ADR-10 · 降级要可见，但「可见」分两层，比例才是要盯的那个数

**背景**：做完 ADR-9 后，单条内容都标了 `aiMode`，界面上也显示「大模型 / 规则引擎」。
但被追问了一句关键的话：*"所以我们现在还是在使用静默降级吗？"*

**第一层反思 —— 单条标注 ≠ 可观测**：
单条标注只能**事后追查**（"这条为什么是模板？"）。
运维真正要盯的是**聚合比例**：模型现在健不健康、失败率是多少、失败原因集中在哪。
没有这一层，模型在生产上静默退化成模板，你依然不会知道。

**第二层反思（更关键）—— 只统计 llm/rule 比例会骗人**：
`aiMode = "rule"` 有**三种完全不同的来源**：

| 来源 | 是不是故障 |
| --- | --- |
| 未配置 key，按设计走规则引擎 | ❌ 不是 |
| 种子数据刻意用规则引擎（离线可复现） | ❌ 不是 |
| **已配置 key，但模型调用失败 / 返回不合法** | ✅ **是** |

如果只统计 llm : rule 比例，演示数据会显示「规则引擎 100%」——
看着像全线故障，实际一切正常。**这样一个会骗人的指标，比没有指标更糟。**

**决策**：给 `Campaign` 和 `GeneratedContent` 增加 `degraded` 布尔字段，
**只有第三种情况才为 true**。于是面板能给出三个独立数字：

```
大模型          32 条  67%
降级             0 条   0%    ← 真正要盯的
规则引擎（按设计） 16 条  33%
```

外加：降级原因分布（按 `aiNote` 聚合）、健康判定文案、活动框架的生成方式。

**健康判定也必须诚实**：种子数据下会出现「大模型 0 条」却「无降级」的组合，
这时候说"模型调用全部正常"是误导 —— 应该说明白：
*"模型已配置且未发生降级；本次活动内容均按设计用规则引擎产出（种子数据预生成），
等有新素材提交就会走模型。"*

另外，一旦有降级，工作台**头部就直接报红**（`AI 降级 N 条`），
不让商家必须翻到概览页才发现。

**配套回归断言**：冒烟测试第 9 节拉取工作台页面，
断言「AI 生成质量」面板存在、区分了「按设计」与「降级」两个概念、
且配了 key 且无故障时显示「零降级」。

## ADR-11 · 认人要防并发，别把 500 甩给老客

**背景**：`getOrCreateContributor()` 原本是「查不到就建」。
但老客双击提交、或同时开了两个标签页时，两个请求都会查不到、都去建，
后一个会撞上 `viewerToken` 的唯一约束 —— 用户看到的是一个 500。

**决策**：create 失败后重读一次。因为此时几乎可以确定是并发同伴刚建好的，
重读就能拿到同一个身份，而不是把错误抛给老客。

```ts
try { return await prisma.contributor.create({ ... }); }
catch { const again = await prisma.contributor.findUnique({ ... }); if (again) return again; throw ...; }
```

免登录 token 认人天然会遇到这个竞态（没有账号体系做前置去重），
所以这条不是"防御性编程"，是这套机制必须付的成本。

## 一个环境层面的踩坑（与产品无关，但卡了很久）

`pnpm install` 的 postinstall 步骤 `prisma generate` 报 `ENOSPC: no space left on device`。
排查发现 **C 盘只剩 20MB**（D 盘还有 100GB+），而 Node / npm / Prisma 会使用 `TEMP` 指向的 C 盘临时目录。

**绕过方式（不改动系统盘任何文件）**：把本项目的 `TEMP` / `TMP` 重定向到 D 盘再执行命令。

```powershell
$env:TEMP = "D:\tmp"; $env:TMP = "D:\tmp"
```

另外 pnpm 的两条坑也记一下，别人 clone 时会遇到：
- `CI=true` 会连带启用 `--frozen-lockfile`，加依赖时必须 `pnpm install --no-frozen-lockfile`
- pnpm 10+ 默认拦截依赖构建脚本，`pnpm-workspace.yaml` 里必须放行
  `prisma` / `@prisma/client` / `@prisma/engines` / `esbuild`，否则别人装不出可用的 Prisma Client

### 一个反复出现的模式：dev server 占着构建产物

这个项目里踩到了**三次同类问题**，值得单独记一笔 —— 都是「dev server 正在运行，
而另一个命令要替换它正在使用的文件」：

| # | 现象 | 原因 | 处理 |
| --- | --- | --- | --- |
| 1 | dev server 全线 500，`Cannot find module './787.js'` | `pnpm build` 清空了 dev 正在用的 `.next` | 已从结构上修掉：build 与 dev 用不同目录（ADR 见 `next.config.ts`） |
| 2 | `prisma generate` 报 `EPERM: rename ...query_engine-windows.dll.node` | dev server 加载了 Prisma 的 native engine DLL，文件被锁 | 停 dev 再 generate。**注意类型定义会更新成功而运行时不会**，所以必须重启 dev，否则旧 client 不认识新字段 |
| 3 | 页面间歇性 500，`SyntaxError: Unexpected end of JSON input` | 强杀 dev server 时 `.next` 里的 JSON 被写到一半 | 停干净后删掉整个 `.next` 重启 |

第 3 条的隐蔽之处在于**间歇性**：同一路径可能这次 200、下次 500。
排查时看到同一 URL 一次成功一次失败，就要立刻想到"构建产物坏了"，
而不是去翻业务代码。**判断依据：`JSON.parse("")` 抛 `Unexpected end of JSON input`。**
