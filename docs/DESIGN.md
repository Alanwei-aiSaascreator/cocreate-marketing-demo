# 设计决策与踩坑记录

这份文档记录的是**为什么这么做**，以及**实际做的时候踩到了什么**。
产品说明和运行方式看 [README](../README.md)。

---

## ADR-1 · AI 层做成「可降级的适配器」而不是直接调模型

**背景**：Demo 要在面试现场演示。现场可能断网、key 可能欠费或限流、模型可能返回不合法的 JSON。

**决策**：`lib/ai/index.ts` 对外只暴露 `generateBlueprint()` 和 `composeContents()` 两个函数，
内部走 `LLM_MODE=auto`：有 key 走模型，**任何一步失败都降级到 `lib/ai/rules.ts` 的规则引擎**，
返回结构完全一致，`aiMode` 字段如实标注走了哪条。

**代价与理由**：
- 代价是要维护两套产出逻辑（约 400 行规则引擎）。
- 收益有两条：演示不会再开天窗；而且**规则引擎本身就是一条质量下限** ——
  模型不可用时产出仍然是「模板 + 老客真实素材拼装」，不是一句「AI 生成失败」。
- 关键细节：降级**不静默**。界面和接口都明说这次是"规则引擎生成"，不糊弄。

**另一层防御**：模型返回的 JSON 会经过
① 去围栏 / 截取花括号 / 修多余逗号的容错解析 → ② zod 结构校验 → ③ 显式归一化。
漏平台、漏图片字段、阈值离谱，都会在 ③ 被补齐，而不是让下游流程崩掉。

## ADR-2 · 模型输出是「不可信输入」，不给它标严格类型

**背景**：最初用 `z.infer<typeof schema>` 直接把模型输出的类型当成领域类型。
结果 zod 的 `.catch()` 让推断类型退化成 `unknown`，`tsc` 报了一串错。

**当时的诱惑**：加几个 `as` 就过去了。

**实际决策**：这个类型错误其实指向了一个真实的设计问题 ——
**模型输出本来就是不可信输入，给它标严格类型本身就是撒谎**。

改为：zod 只负责"形状对不对、核心字段在不在"，校验通过后得到的是**宽松类型**
（`RawPlatformFrame` / `RawTaskField` / `RawRewardTier`），
再由 `ensureFrames()` / `ensureTaskCard()` / `ensureRewardTiers()` 显式转成严格领域类型。
`llmJson<T>()` 的 schema 参数改成不带泛型的 `ZodType`，由调用方显式声明 `T`。

这样"归一化"从一个隐含动作变成了一个**显式的、可读的步骤**。

## ADR-3 · 奖励阈值属于经济规则，不让模型决定

**背景（实测踩坑）**：真实调用模型生成活动蓝图，产出的奖励阶梯是：

```json
[{"threshold": 1, "name": "参与礼"}, {"threshold": 3, "name": "优质内容礼"}, {"threshold": 5, "name": "共创达人礼"}]
```

**问题**：本系统的贡献值尺度是 —— 提交一份合格素材单次就能拿 50 分（基础 20 + 实拍图 10 + 细节 5 + 完整 5 + 首次 10）。
阈值 1 / 3 / 5 意味着**老客提交一次就解锁全部三档福利，商家预算瞬间被击穿**。

**根因**：模型不知道我们的积分尺度，它按"1-5 分"的直觉给阈值。

**决策**：调提示词（把积分经济写清楚并锚定 50~300）**只是第一层**，
真正的兜底是在 `lib/domain/scoring.ts` 里定义 `canonicalThresholds(n)`：

```
1 档 → [50]      3 档 → [50, 120, 260]
2 档 → [50, 150] 4 档 → [50, 100, 180, 300]
```

`ensureRewardTiers()` 保留模型写的**档位名、福利内容、面额**（这是它擅长的），
但 `threshold` 一律强制映射到这个阶梯上（这是确定性的）。

**原则**：**AI 出内容，规则定经济。** 凡是"算得出来"的东西，不要交给模型。
提示词里也同步写明了积分经济和"不要自己发明量级"，让模型的档位语义（尝鲜 → 常客 → 铁粉）合理。

## ADR-4 · 严格区分「第一人称体验」和「店铺客观信息」

**背景（实测踩坑）**：老客提交的素材里只有**锅底**和**冰粉**（服务员送冰粉的细节），
但模型产出的小红书正文里出现了：

> **2. 凌晨到的鲜毛肚：毛肚是当天凌晨到的鲜货，下锅几秒就能吃，脆得很直接。**

老客根本没提交过毛肚 —— 模型把我在 `mustInclude` 里写的**商家卖点**，当成了老客的体验写进了「真实体验」分点里。

**严重性**：这条直接打脸整个产品主张（"不编造老客没提到的体验"），
而且是**我自己的设计自相矛盾**：一边在框架里要求"必含卖点"，一边在加工提示词里要求"只用素材事实"。

**决策**（两处一起改）：
1. `prompts.ts` 的 `COMPOSE_SYSTEM` 里加死规则：第一人称体验只能来自素材；
   店铺客观信息可以来自商家资料，但**必须写成客观陈述**（「他们家主打 X」），
   绝不能写成「我吃了 X，很香」；老客没提到的招牌只能作为店铺介绍一笔带过，
   不得出现在「真实体验」「推荐」这类第一人称分点里。
2. `rules.ts` 的 `mustInclude` 里，商家卖点明确标注为
   「**只能作客观店铺信息提及，不得写成老客的亲身体验**」。

**修复后实测效果**：

| 平台 | 修复前 | 修复后 |
| --- | --- | --- |
| 小红书 | 「毛肚…下锅几秒就能吃，脆得很直接」（第一人称分点） | 正文只讲锅底和冰粉，正文完全不提毛肚 |
| 抖音 | 「毛肚是凌晨到的鲜货，下锅几秒就脆」（口播） | 「他们家还有凌晨到的鲜毛肚，**下次来试试**」 |
| 点评 | 混在「推荐」里 | 「另外店里主打凌晨到的鲜毛肚，**新鲜度是卖点**」 |

模型开始主动承认自己没吃过 —— 这个区别就是"共创"和"AI 编稿"的分界线。

**遗留限制**：这仍然是**提示词约束，不是硬校验**。生产环境应再加一层
「素材实体比对」：把产出里的菜名/价格/服务描述与素材做实体级比对，命中素材中不存在的就转人工复核。

## ADR-5 · 贡献值必须「可拆解」，而不是一个黑盒数字

**决策**：`scoreSubmission()` 产出的不是一个数字，而是 `PointItem[]`：每条得分都有
`label`（做了什么）、`points`（多少分）、`note`（**为什么给这个分**）。

```
提交合格素材          +20   保底分，鼓励参与
提供实拍图            +10   实拍图是可信度的地基
补充了具体细节        +5    细节是 AI 编不出来的东西
素材完整度高          +5    必填项全部填写
首次参与本活动        +10   新人加权，让第一次参与就能拿到第一档福利
图片重复              -20   同活动内已收到过相同图片
──────────────────────────
内容被商家采用        +30   质量导向（采用时追加）
带来有效点击回流      +5/次 绑定真实引流效果（封顶 50）
```

**为什么**：这套机制要同时约束两方，而两方都需要"讲得通"：
- 老客要看到「怎么做才能拿更多」，否则不会持续贡献；
- 商家要看到「这笔钱花在哪了」，否则不敢放预算。

所以界面上（H5 结果页、贡献明细、素材与风控 Tab）每一处都展示完整拆解和原因。

## ADR-6 · 引流归因用一张 `TrackEvent` 表兜住

**决策**：每条 AI 内容带一个 `shareToken`，分享落地页 `/s/[shareToken]` 在加载时记 `view`、
点 CTA 时记 `click`，`click` 触发贡献值 +5。

**为什么这是必需品而不是加分项**：没有它，"奖励绑定真实引流效果"就只是 PPT 上的一句话。
有了它，演示时能当场发生：面试官用手机点一下，贡献者的贡献值在商家后台的贡献榜上当场变化。

**三条防刷规则**（都在 `app/api/track/route.ts`）：
1. 同一个访客对同一条内容只计一次有效回流（按 viewerToken 去重）
2. **自己点自己的分享不计分** —— 否则这条链路的分数毫无意义
3. 单项封顶 50 分 —— 避免一条爆款内容把商家的福利预算打穿

## ADR-7 · 免登录身份：cookie 要在**本次请求**就能被读到

**背景**：老客要免登录参与，就不能有账号体系。用 `middleware.ts` 下发一个 `cc_viewer` cookie 来认人。

**踩到的细节**：写 `response.cookies.set()` 只对**下一次**请求生效，
首次访问的服务端组件读不到这个 cookie，于是"第一次进来的人不知道自己是谁"，
提交时才会创建身份，导致页面上的"我的贡献值"永远是 0。

**解决**：middleware 在写 response cookie 的同时，把 token 塞进请求头 `x-cc-viewer` 转发下去；
`lib/viewer.ts` 的 `readViewerToken()` **优先读请求头、退化读 cookie**。
这样首次访问和后续访问的行为一致。

## ADR-8 · 不引外部字体、不引第三方二维码服务

**决策**：放弃 `next/font/google`（create-next-app 默认带 Geist），改用系统字体栈；
二维码用 `qrcode` 包在服务端出图，不请求外部生成服务。

**理由**：都是为了**构建期和运行期不依赖外网**。字体下载失败会让整个 Demo 掉样式，
这在演示场景里是不可接受的失败模式。"能离线跑"是这个项目的硬约束。

## ADR-9 · 逐条校验，别让一个字段吃掉整批 AI 产出

**背景（实测踩坑）**：老客提交素材后，界面一切正常、贡献值和福利照常发放，
但内容库里的东西全是模板拼的 —— 大模型明明配置正常。

翻 `aiNote` 才看到真正的原因：

```
模型调用失败，已自动降级到规则引擎。
原因：结构校验失败: contents.3.title String must contain at least 1 character(s)
```

模型返回了 4 条内容，但**第 4 条（朋友圈）的 `title` 是空的** ——
朋友圈本来就没有标题，模型留空完全合理。而我那条 `title: z.string().min(1)`
让**整批 4 个平台一齐被判失败**，全部退回模板。

**这是 AI 层最危险的失败模式**：不是报错、不是崩溃，而是**静默降级** ——
界面上看不出任何异常，但产品的核心主张（AI 加工质量）已经完全落空。
如果不是我习惯性去打 `aiNote`，它会一直藏着。

**决策**（三处一起改）：

1. **容器只管形状，元素逐条校验。**
   `blueprintSchema` / `composeBundleSchema` 从
   `z.array(itemSchema).min(n)` 改成 `z.array(z.unknown())`，
   元素由 `parseEach()` 逐条 `safeParse`：坏一条只丢那一条，由规则引擎单独补齐。

2. **区分「字段缺失」和「字段为空」。**
   标题这类**平台语义上允许为空**的字段改为 `.catch("")`，
   再由归一化补兜底值（正文首行 → 平台名）。
   真正不能空的（`body`）才保持 `min(1)`。

3. **如实汇报，不假装是 AI 产出的。**
   模型一条可用的都没给出时，`aiMode` 标成 `rule` 而不是 `llm`；
   `aiNote` 里明确写出「丢弃 N 项不合法产出」「N 个平台由规则引擎补齐」。

**配套的回归断言**（`scripts/smoke-test.mjs`）：读 `.env` 判断是否配置了 key，
若配置了，就断言 `aiMode === "llm"` 且 `aiNote` 里不出现「降级/补齐/不合法」。
**静默降级从此不可能再悄悄回来。**

**顺带发现**：同一条测试里，重复使用同一张图片提交时贡献值从 50 掉到 30 ——
不是 bug，是 `duplicate_image` 扣 20 分的防刷规则正确生效。

## ADR-10 · 降级要可见，但「可见」分两层，比例才是要盯的那个数

**背景**：做完 ADR-9 后，单条内容都标了 `aiMode`，界面上也显示「大模型 / 规则引擎」。
但被追问了一句关键的话：*"所以我们现在还是在使用静默降级吗？"*

**第一层反思 —— 单条标注 ≠ 可观测**：
单条标注只能**事后追查**（"这条为什么是模板？"）。
运维真正要盯的是**聚合比例**：模型现在健不健康、失败率是多少、失败原因集中在哪。
没有这一层，模型在生产上静默退化成模板，你依然不会知道。

**第二层反思（更关键）—— 只统计 llm/rule 比例会骗人**：
`aiMode = "rule"` 有**三种完全不同的来源**：

| 来源 | 是不是故障 |
| --- | --- |
| 未配置 key，按设计走规则引擎 | ❌ 不是 |
| 种子数据刻意用规则引擎（离线可复现） | ❌ 不是 |
| **已配置 key，但模型调用失败 / 返回不合法** | ✅ **是** |

如果只统计 llm : rule 比例，演示数据会显示「规则引擎 100%」——
看着像全线故障，实际一切正常。**这样一个会骗人的指标，比没有指标更糟。**

**决策**：给 `Campaign` 和 `GeneratedContent` 增加 `degraded` 布尔字段，
**只有第三种情况才为 true**。于是面板能给出三个独立数字：

```
大模型          32 条  67%
降级             0 条   0%    ← 真正要盯的
规则引擎（按设计） 16 条  33%
```

外加：降级原因分布（按 `aiNote` 聚合）、健康判定文案、活动框架的生成方式。

**健康判定也必须诚实**：种子数据下会出现「大模型 0 条」却「无降级」的组合，
这时候说"模型调用全部正常"是误导 —— 应该说明白：
*"模型已配置且未发生降级；本次活动内容均按设计用规则引擎产出（种子数据预生成），
等有新素材提交就会走模型。"*

另外，一旦有降级，工作台**头部就直接报红**（`AI 降级 N 条`），
不让商家必须翻到概览页才发现。

**配套回归断言**：冒烟测试第 9 节拉取工作台页面，
断言「AI 生成质量」面板存在、区分了「按设计」与「降级」两个概念、
且配了 key 且无故障时显示「零降级」。

## ADR-11 · 部分降级也是降级，别让整批标签撒谎

**背景**：被问「什么情况下会降级」时，我照着代码逐条数，才发现**自己漏了一整类**。

`composeContents()` 里模型可能只给出 4 个平台中的 3 个，第 4 个由规则引擎补齐。但当时这段是：

```ts
const contents = targets.map((p) => modelContents.get(p) ?? ruleCompose(...));
const filled = targets.length - modelContents.size;
...
return { contents, aiMode: "llm", degraded: false, note: ... };  // ← filled > 0 时也这样返回
```

于是**模型只给 3/4 个平台**时：
- 那条规则引擎拼出来的内容，在数据库里被标成 `aiMode = "llm"` —— **标签在撒谎**
- 整批 `degraded = false` —— **面板显示「零降级」，看不见这次有 1/4 的内容是模板**

比"漏统计"更糟：这是**数据本身写错了**，事后追查也会被误导。

**决策**：把来源从「整批一个」改成「**逐条各自一份**」。

```ts
interface ComposedItem extends ComposedContent {
  source: AiMode;    // 这一条的真实来源
  fallback: boolean; // 这一条是不是兜底产出
}
```

| 情况 | source | fallback |
| --- | --- | --- |
| 模型写的 | `llm` | `false` |
| 规则引擎补的（模型没给这个平台） | `rule` | `true` |
| 整批退回模板 | `rule` | `true` |
| 未配 key / 种子数据 | `rule` | `false`（按设计，不是兜底） |

批次级 `degraded = contents.some(c => c.fallback)` —— **部分降级也是降级**。
活动蓝图同理：平台框架缺、任务卡字段不足被整张替换、奖励阶梯档位不足、丢弃了不合法产出，
任何一处靠规则顶上，都算部分降级。

**面板相应改成三态**，避免「部分」和「全部」混为一谈：

| 状态 | 含义 |
| --- | --- |
| `健康 · 零降级` | 模型全部正常 |
| `部分降级 · N/M 条退回模板`（琥珀色） | 模型输出不稳定，部分平台靠规则补齐 |
| `不健康 · 全部降级（N 条）`（红色） | 模型整体不可用 |

**配套回归断言**（冒烟测试第 3 节）：
- 每条内容的 `source` 与 `fallback` 必须自洽（`llm ⟺ !fallback`）
- 批次 `degraded` 必须等于「是否存在任何一条 `fallback`」

**反思**：这个盲区是被一个提问逼出来的 ——「什么情况下会降级」。
凭记忆答很容易漏，是**照着代码逐条数**才发现的。写实现的人最容易高估自己实现的完备性。

## ADR-12 · 认人要防并发，别把 500 甩给老客

**背景**：`getOrCreateContributor()` 原本是「查不到就建」。
但老客双击提交、或同时开了两个标签页时，两个请求都会查不到、都去建，
后一个会撞上 `viewerToken` 的唯一约束 —— 用户看到的是一个 500。

**决策**：create 失败后重读一次。因为此时几乎可以确定是并发同伴刚建好的，
重读就能拿到同一个身份，而不是把错误抛给老客。

```ts
try { return await prisma.contributor.create({ ... }); }
catch { const again = await prisma.contributor.findUnique({ ... }); if (again) return again; throw ...; }
```

免登录 token 认人天然会遇到这个竞态（没有账号体系做前置去重），
所以这条不是"防御性编程"，是这套机制必须付的成本。

## ADR-12 · 「我以为修好了」——验证必须打到持久层

**背景**：ADR-11 说「逐条记录真实来源」修完了。做一次完整自查（含一路独立代码审查）后发现：
**只改了函数返回值和 API 响应，数据库写入那一行还是整批值。**

```ts
// app/api/c/[token]/submit/route.ts —— 修完 ADR-11 之后仍然是这样
aiMode: composed.aiMode,      // ← 整批值，不是逐条 item.source
degraded: composed.degraded,
```

后果比原来更糟：那条规则引擎拼的内容在库里**依然**被标成 `aiMode = "llm"`，
而且面板会算出 `ruleByDesign = 4 - 4 - 4 = -4`，渲染出「-4 条」「-100%」，
健康判定还会从「部分降级」直接跳到红色「全部降级」。

**为什么会漏**：当时我并行发了两个编辑，都因「未读取文件」被拒；
重新读取后我只补交了其中一个，却在总结里当成两个都改完了。

**真正的教训不是"要细心"，而是：**

> 一次改动跨越「函数 → 接口 → 持久层 → 展示层」时，
> **验证必须打到最外层（数据库里实际存了什么），而不是停在改到的那一层。**
> 断言写在返回值上，就永远发现不了持久层没跟上。

**配套修复**：
- 写库改成逐条 `item.source` / `item.fallback`
- 面板三个数字改成**各自独立统计**（不再用总数反推），从结构上不可能为负
- 冒烟测试断言改成**单向蕴含**：`fallback ⟹ rule`。
  原来写成了双向等价，而「按设计走规则引擎」也是 `rule` 但 `fallback=false` ——
  那条断言在**任何没配 key 的机器上都会失败**，等于给别人的第一印象是"测试挂了"。

## ADR-13 · 并发保护必须在数据库层，不能在应用层「先查后插」

**背景**：代码里有三处幂等保护，写法都是「先查有没有，没有就插」：

```ts
const exists = await prisma.contribution.findFirst({ where: { submissionId, reason } });
if (!exists) await prisma.contribution.create({ ... });
```

两个请求并发时**都会查到"没有"**，于是都插入。而代码注释还写着
「反复点采用不会重复加分」「结算只能有一份，避免分数和券对不上」—— 承诺是假的。

实测能造成的后果：
- 双击「采用」→ 一条内容拿 60 分（应为 30）
- 两个标签页同时提交 → 同一档位发两张券，且都拿到「首次参与 +10」
- 不带 cookie 连发 10 次点击 → 每次都被 middleware 发一个新身份，刷满封顶

**决策**：把幂等下沉为数据库约束，应用层查询只作为快速路径。

```prisma
Reward      @@unique([campaignId, contributorId, tierName])
Contribution @@unique([submissionId, reason])
Contribution @@unique([firstClaimKey])   // 「首次参与 +10」的名额
TrackEvent  @@unique([contentId, type, viewerKey])
```

**「首次参与 +10」这一条是最后才补上的**，因为它比前两条棘手得多：
前两条的冲突对象是「同一份素材 / 同一条内容」，一个唯一键就够；
而它的冲突对象是**一对（活动, 老客）** —— 两次并发提交的 `submissionId` 本来就不同，
`@@unique([submissionId, reason])` 根本挡不住。

解法是让数据库**发名额**：抢到的请求保留这 10 分，并把 claim key（`first:<campaignId>:<contributorId>`）
写进自己的贡献记录；没抢到的那个撞上 P2002，就去掉这 10 分重新计分，
并同步改正已经落库的 `submission.points` 和返回给老客的 `points` ——
否则界面上显示的分数会比他实际拿到的多，那又变成了一次「承诺与行为不一致」。

写入口只在捕获 `P2002` 时跳过，**其它错误必须照抛** ——
静默吞掉数据库故障会让「券没发出去」变得无声无息。

**点击刷分的额外修复**：访客身份不能再用 middleware 注入的 `x-cc-viewer` ——
那个 token 在 cookie 缺失时是**每次请求现场新生成的 UUID**，脚本换个身份就能重复刷。
改成只认稳定来源：真实 cookie，没有就退化用 IP + User-Agent 的哈希。
加分放进 `$transaction`，并发下不会超发封顶。

## ADR-14 · 撒谎注释清单（都是我自己造的）

自查时专门找了一类问题：**注释/文案声称做了某事，代码里却没有。**
这种问题比 bug 更坏 —— 它让读代码的人（包括未来的我）建立错误的心智模型。

| 位置 | 注释/文案说了什么 | 代码实际做了什么 | 修法 |
| --- | --- | --- | --- |
| `LLM_MODE=llm` | 「强制走模型，失败即报错」 | 与 `auto` 完全一样，失败照样静默退回模板 | 真加严格模式：`llm` 下失败直接抛错 |
| 频次限制提示 | 「超出部分不计入有效贡献」 | 什么都没做，第 4 次起照样拿满分；计数口径也不是"今天"而是全活动累计 | 真实现规则（超出便捷次数后基础分 20→5）并把文案改准 |
| 风控禁词提示 | 「AI 会在加工时替换成安全说法」 | 走大模型时提示词能做到，但**走规则引擎时只标记、原文保留** | `ruleCompose` 里真做替换（只替长且无歧义的词，拿不准的不动并标出） |
| `compare-engines.ts` | 「模型有问题会直接报错暴露出来」 | 同上，不会报错，会打印一段模板内容并正常退出 | 随严格模式一起生效 |
| `next.config.ts` | 把 build 与 dev 的产物目录分开 | `start` 没跟着走 → `pnpm build && pnpm start` 找不到生产构建 | `start` 也走同一目录 |

**规则**：写「注释承诺」的时候，顺手去代码里确认一遍它真的成立。
做不到的事就不写，或者写成「已知限制」。

## ADR-15 · 模型生成的字段名不能成为系统的隐式契约

**背景**：任务卡是 AI 生成的，字段 `id` 由模型自由决定。但代码里到处按固定 id 取值：

- `scoring.ts`：只有 `answers.detail` 才给「具体细节 +5」
- `risk.ts`：`answers.feeling` 才进灌水检测
- `rules.ts`：按 `feeling` / `recommend` / `scene` / `detail` 拼正文
- `SubmitForm.tsx`：`choice` 选项的中文标签硬编码在前端，只认 5 个英文 key

模型把 `feeling` 写成 `experience`、或把选项写成 `with_friends`，后果**全是静默的**：
那 5 分永远拿不到且 breakdown 里看不到、H5 直接显示英文 id、
正文里出现「with_friends 过来的。」、商家侧的「原始素材」面板变空白。

**决策**：两层归一化，让系统不依赖模型的命名习惯。

1. **字段 id 归一化**：维护一张同义词表（`experience` / `impression` / `感受` → `feeling`），
   归一化后再保证五个语义字段齐全 —— 缺的用规则引擎版本补上。
2. **选项直接用中文**：选项值本身就是「和朋友聚会」，前端直接渲染、规则引擎直接入文。
   英文 key → 中文的映射只保留一份用于兼容历史数据。

**原则**：凡是系统要按名字取的东西，名字就不能由模型自由发挥；
要么在契约里固定，要么在入口处归一化。

## ADR-16 · 商家侧最简口令：默认放开，但绝不隐形

**背景**：代码审查把「4 个商家写接口零鉴权」列为严重问题 ——
任何人 POST 一下就能核销任意老客的券、采用内容、反复重建活动框架（每次真调一次大模型）。

**决策**：`MERCHANT_PASSWORD` 环境变量，默认留空。

- **留空 = 演示模式**，接口完全放开。之所以默认放开：这是个要给人当场演示的东西，
  加一道登录会挡住"打开就能看"的体验。
- **但界面上必须显式标注**「演示模式 · 未鉴权」，并写清后果
  （不能直接放公网）和开启方式。安全缺口最危险的状态不是"存在"，而是"存在但没人知道"。
- 设置后：页面 307 跳口令页、接口 401，cookie 为 `httpOnly` 的哈希值（不存明文口令）。

**明确不是生产方案**（写进了 README 和 `.env.example`）：生产还需要商家账号体系、
**资源归属校验**（核销时确认这张券属于当前商家，现在只校验"你是否是商家"）、写接口限流。

**顺带一条设计取舍**：只拦写接口和页面，不拦整个站点的读接口 ——
如果 `/api/merchant/*` 的 GET 也一律 401，前端会拿到一个 JSON 报错而用户完全看不懂。
**失败要说人话，而不是回一个状态码。**

## ADR-17 · 验证方法本身也可能是错的

这一轮自查里，我**三次**得出过错误结论，每一次都是"验证工具"而不是"被测代码"有问题：

| 我的结论 | 真相 | 教训 |
| --- | --- | --- |
| 「全新 clone 装不上：`prisma generate` 需要 `.env`」 | 它**不需要**（实测无 .env 也能跑通）。真实原因是 dev server 锁住了 Prisma 的 engine DLL | 我差点照错误假设提交一个修复 + 一条撒谎注释 |
| 「`/merchant` 没被拦截（返回 200）」 | 实际返回 **307** 跳口令页。是 PowerShell 的 `-MaximumRedirection 0` 不抛异常，而我没打印状态码就下了结论 | **没看到状态码就不要下结论** |
| 「冒烟测试登录失败」 | 登录成功了，是 `...merchantHeaders` 被放在 fetch 配置的**顶层**而不是 `headers` 内，cookie 从没发出去 | 把辅助函数改成"失败必须喊出来"之后，问题立刻从"登录失败"缩小到"cookie 没发出去" |

**沉淀成三条规则**：

1. **被测对象以外的东西也要验证。** 测试脚本、临时命令、PowerShell 的默认行为，
   都可能是错误的来源。两次"修复没生效"其实是验证方式错了。
2. **辅助函数不许静默失败。** `if (!res.ok) return;` 这种写法会把真实原因藏起来，
   让后续断言以假象失败（一片 401 看起来像功能坏了，其实只是测试没带凭据）。
   改成 `process.exit(1)` 并打印原因。
3. **断言要打在能被观察的地方。** 上一轮我把断言写在函数返回值上，于是持久层没改也"通过"了
   （见 ADR-12）。验证必须打到最外层。

## ADR-18 · 两版产出共存，但质量比例只统计「当前采用的那一版」

**背景**：种子数据用规则引擎生成（为了离线可复现），`demo:ai` 又用大模型重跑一遍。
最初的实现是**直接覆盖** —— 规则引擎写的那 184 段文案被顶掉了。于是有人问：
「你是不是把上一次的规则引擎数据删掉了？」

**问题不只是"删数据"**：规则引擎产出**本身就是最好的教学材料**。
切过去能直接看到模板拼装的毛病 —— 标题被硬截断
（`成都这家火锅店，锅底是真的香，牛油味很…`）、分点撞车（推荐项和卖点重复成
`1️⃣ 手工现炒牛油锅底` 和 `2️⃣ 手工现炒牛油锅底`）、偶尔出病句（`人均：人均 98 。`）。
把这份证据删掉，等于放弃了"为什么需要 AI"最有说服力的论据。

**决策**：`GeneratedContent` 增加两个字段，让两版共存。

```prisma
variant   String  @default("llm")   // llm | rule
isPrimary Boolean @default(true)    // 是否是"当前采用/展示"的那一版
@@unique([submissionId, platform, variant])
```

`demo:ai` 从「覆盖」改成「建配对」：补一份规则引擎对比版（本地生成、零成本），
大模型版作为 primary，两版挂在同一素材下。**谁都不覆盖谁。**

**关键的一条：质量面板只统计 `isPrimary`。**

这是这个设计里最容易做错的地方 —— 如果给每条内容都存一份对比版、然后把所有行都算进比例，
面板会显示「大模型 50% / 规则引擎 50%」，**比不统计更误导人**。

所以：内容库计数、闭环漏斗、质量比例只看 primary；对比版**单独报一个数**，
并在面板上明确写出**「未计入以上比例」**。

**顺带修正一处诚实性问题**：模型重试三次仍失败时**不创建 llm 版**，
而是把规则引擎版标成 `degraded = true`。因为这时的规则产出确实是
"本该走模型却失败了"的兜底，不是"按设计如此"。
不这么标的话，面板会把它误报成健康的「规则引擎（按设计）」。

**另一个教训**：改完之后脚本的汇总报了「成功 0、失败 65」—— 那 65 条其实是
"本来就有大模型版、本次只补了对比版"。混成一个成功/失败计数，就是把正常情况误报成失败。
**汇总本身也会撒谎**，所以拆成了三档：本次生成 / 复用已有的 / 真失败。

## ADR-19 · 密钥要能在界面里填，但界面绝不回显它

**背景**：有人问「你没把我的密钥写死在代码里吧？给一个窗口让用户输入密钥」。
前半句是安全确认（已全历史核查：密钥只在 `.env`，14 个提交与所有历史快照里都不存在），
后半句是个真实的产品缺口 —— 别人 clone 下来必须去改 `.env` 再重启，门槛太高。

**决策**：新增 `Setting` 键值表 + `/merchant/settings` 页面。

**优先级：界面设置 > 环境变量（.env）。**
这样 CI / 部署环境仍然可以只用环境变量，而界面上填过的会覆盖它 ——
避免"我刚刚在界面上填了 key 怎么不生效"。

**几个必须做对的细节：**

1. **保存后立即生效，不重启。**
   难点是 `llmConfig()` 是同步函数（AI 层到处在调），而读数据库是异步的。
   做法是一层内存缓存：AI 入口先 `await ensureSettingsLoaded()`，
   之后 `effectiveAiSettings()` 就能同步读到；保存时同步更新缓存。
   缓存未加载时**退化成只读 .env**，不会因为设置读不到就把 AI 关掉。

2. **留空 = 删除该项，而不是存空字符串。**
   否则一个空的 `ai.apiKey=""` 会把 `.env` 里的 key 挡住，
   用户会看到"我明明 .env 里配了 key 却说不启用"。

3. **读接口只返回掩码。** 密钥只写不读，写进去之后只能整体替换或清空。
   冒烟测试里有一条断言专门守这个：**真实密钥不得出现在任何页面的 HTML 里**。

4. **测试连接做成一等公民。**
   这是这个页面上最有用的一步 —— 让用户当场知道 key 能不能用，
   而不是保存完、去提交一条素材、才发现不行。

5. **存储方式如实说明，不假装安全。**
   明文存本地 SQLite；页面上明确写出"生产应走 KMS/Vault 或加密存储"，
   以及"没设 `MERCHANT_PASSWORD` 时这个页面在公网是开放的，别填真 key"。
   **安全的界面比安全的实现更容易骗人** —— 一个不说明存储方式、只显示"已加密"的页面
   比老老实实写"明文存储"更危险。

**顺带修的**：设置页最初是纯客户端取数，首屏是"加载中"空壳 —— 既不好看也不可测。
改成服务端把状态取好传给表单，于是冒烟测试能断言"设置页服务端就渲染出表单"。

## 一个环境层面的踩坑（与产品无关，但卡了很久）

`pnpm install` 的 postinstall 步骤 `prisma generate` 报 `ENOSPC: no space left on device`。
排查发现 **C 盘只剩 20MB**（D 盘还有 100GB+），而 Node / npm / Prisma 会使用 `TEMP` 指向的 C 盘临时目录。

**绕过方式（不改动系统盘任何文件）**：把本项目的 `TEMP` / `TMP` 重定向到 D 盘再执行命令。

```powershell
$env:TEMP = "D:\tmp"; $env:TMP = "D:\tmp"
```

另外 pnpm 的两条坑也记一下，别人 clone 时会遇到：
- `CI=true` 会连带启用 `--frozen-lockfile`，加依赖时必须 `pnpm install --no-frozen-lockfile`
- pnpm 10+ 默认拦截依赖构建脚本，`pnpm-workspace.yaml` 里必须放行
  `prisma` / `@prisma/client` / `@prisma/engines` / `esbuild`，否则别人装不出可用的 Prisma Client

### 一个反复出现的模式：dev server 占着构建产物

这个项目里踩到了**三次同类问题**，值得单独记一笔 —— 都是「dev server 正在运行，
而另一个命令要替换它正在使用的文件」：

| # | 现象 | 原因 | 处理 |
| --- | --- | --- | --- |
| 1 | dev server 全线 500，`Cannot find module './787.js'` | `pnpm build` 清空了 dev 正在用的 `.next` | 已从结构上修掉：build 与 dev 用不同目录（ADR 见 `next.config.ts`） |
| 2 | `prisma generate` 报 `EPERM: rename ...query_engine-windows.dll.node` | dev server 加载了 Prisma 的 native engine DLL，文件被锁 | 停 dev 再 generate。**注意类型定义会更新成功而运行时不会**，所以必须重启 dev，否则旧 client 不认识新字段 |
| 3 | 页面间歇性 500，`SyntaxError: Unexpected end of JSON input` | 强杀 dev server 时 `.next` 里的 JSON 被写到一半 | 停干净后删掉整个 `.next` 重启 |

第 3 条的隐蔽之处在于**间歇性**：同一路径可能这次 200、下次 500。
排查时看到同一 URL 一次成功一次失败，就要立刻想到"构建产物坏了"，
而不是去翻业务代码。**判断依据：`JSON.parse("")` 抛 `Unexpected end of JSON input`。**
